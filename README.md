## ۱. خلاصه

یک Agent پایتونی که مسائل استدلالی فارسی (جبر، منطق، زمان‌بندی، شمارش، مسیر، تخصیص با قید، راستگو/دروغگو و...) را فقط با مدل لوکال Qwen روی Ollama حل می‌کند. خروجی همیشه یک `output.json` معتبر با همان `id` و یک رشته‌ی `answer` است که فقط جواب نهایی را دارد.

- همه‌ی inference فقط با Ollama روی localhost است. هیچ API ابری و هیچ اینترنتی در زمان اجرا استفاده نمی‌شود.
- هیچ جدول جواب، هیچ تشخیص مستقیم مسائل Public و هیچ حل‌کننده‌ی brute-force در `main.py` نیست. جواب فقط از استدلال مدل می‌آید.
- ابزارهای brute-force فقط برای ساخت کلید جواب تست در پوشه‌ی توسعه (`dev_tools/`، جزو فایل‌های تحویلی نیست) بوده‌اند و هیچ‌وقت در `main.py` وجود ندارند.

## ۲. نصب و اجرا

```bash
# ۱) Ollama را نصب کنید و مدل را یک‌بار pull کنید (فقط همین مرحله اینترنت می‌خواهد)
ollama pull qwen3.8:27b        # مدل ارزیابی؛ برای توسعه روی سیستم ضعیف‌تر: qwen3:8b
# ۲) وابستگی‌ها
pip install -r requirements.txt
# ۳) اجرا (بدون اینترنت)
python main.py --input input.json --output output.json
```

نمونه ورودی: `{"id": "test_001", "problem": "متن مسئله"}` و نمونه خروجی: `{"id": "test_001", "answer": "FINAL_ANSWER"}`. ورودی به‌صورت لیستی از چند مسئله هم پذیرفته می‌شود.

### انتخاب مدل (اسم مدل داخل کد ثابت نیست)
ترتیب: ۱) آرگومان `--model` یا متغیر محیطی `AGENT_MODEL` ← ۲) `qwen3.8:27b` اگر با `ollama list` نصب بود ← ۳) `qwen3:8b` ← ۴) هر مدل qwen نصب‌شده.

### تنظیمات اختیاری
| آرگومان / متغیر | توضیح | پیش‌فرض |
|---|---|---|
| `--think off/on/auto` یا `AGENT_THINK` | حالت thinking مدل Qwen3 | `off` |
| `--max-calls` یا `AGENT_MAX_CALLS` | سقف فراخوانی مدل برای هر مسئله | ۶ (مدل کوچک)، ۵ (مدل بزرگ) |
| `--time-limit` یا `AGENT_TIME_LIMIT` | سقف نرم زمان هر مسئله (ثانیه) | ۳۰۰ (کوچک)، ۴۵۰ (بزرگ) |
| `--rewrite` | مرحله‌ی اختیاری پاک‌سازی/بازنویسی مسئله | خاموش |
| `--hints` یا `AGENT_HINTS=1` | افزودن راهنمای تکنیک (مثلاً جستجوی لایه‌به‌لایه در شبکه) به پرامپت | خاموش (تا وقتی eval ثابت کند کمک می‌کند) |
| `OLLAMA_HOST` | آدرس سرور Ollama لوکال | پیش‌فرض Ollama |

مقادیر پیش‌فرض سقف زمان و فراخوانی حدس من هستند چون حدود رسمی ارزیابی را نمی‌دانم؛ با آرگومان‌ها قابل تغییرند. `num_ctx` صریحاً روی ۸۱۹۲ تنظیم شده تا متن مسئله بریده نشود.

## ۳. معماری

```
مسئله ─► ۱. نرمال‌سازی (ارقام فارسی/عربی ← انگلیسی)         [Python]
      ─► ۲. تشخیص قالب جواب (regex؛ فقط اگر نشد یک فراخوانی کوتاه) [Python / مدل]
      ─► ۳. (اختیاری) پاک‌سازی مسئله                             [مدل]
      ─► ۴. حل مستقل در سبک‌های مختلف + Self-Consistency تطبیقی    [مدل]
      ─► ۵. استخراج و اعتبارسنجی هر جواب با regex                 [Python]
      ─► ۶. رأی‌گیری روی جواب نهایی؛ تساوی ← کوچک‌ترین در ترتیب طبیعی [Python]
      ─► ۷. در صورت شکست: salvage از متن خروجی، و در نهایت Fallback با قالب معتبر
```

نکات طراحی و ارتباط با اسلایدهای درس:

- **Chain of Thought:** همه‌ی حل‌ها قدم‌به‌قدم‌اند. سه سبک داریم: قدم‌به‌قدم ساده، Least-to-Most (شکستن به زیرسؤال) و Analogical (اول مسئله‌ی مشابه). Planner جدا نداریم، چون Least-to-Most همان شکستن به زیرمسئله را در همان فراخوانی انجام می‌دهد و فراخوانی کمتر می‌شود.
- **Self-Consistency تطبیقی:** اول دو حل مستقل (دما بالاتر از صفر). اگر جواب نهایی یکی بود، تمام. اگر نه، نمونه‌ی بیشتر تا سقف بودجه، و توقف به محض اینکه یک جواب حداقل دو رأی و برتری روشن داشته باشد. رأی‌گیری فقط روی جواب نهایی نرمال‌شده است نه متن استدلال، پس «۱۲»، «12» و «12.» یکی حساب می‌شوند.
- **بدون بازبینی توسط خود مدل:** طبق اسلایدها مدل بدون داور بیرونی نمی‌تواند جواب خودش را درست اصلاح کند. پس تنها بررسی‌ها با کد پایتون است (قالب، محدوده‌ی مجاز گزینه‌ها).
- **اطلاعات بی‌ربط:** در پرامپت صریحاً گفته شده نادیده گرفته شود، و مرحله‌ی بازنویسی اختیاری هم هست. چون ممکن است چیز لازم حذف شود، پیش‌فرض خاموش است و در مرحله‌ی بازنویسی هم متن اصلی مرجع می‌ماند. فقط اگر `eval.py` بهبود نشان داد روشن شود.
- **ترتیب قیود:** پرامپت از مدل می‌خواهد ابتدا داده‌ها و قیود را به ترتیب منطقی فهرست کند.
- **حافظه‌ی context:** هر حل مستقل است و فقط جواب نهایی استخراج‌شده منتقل می‌شود، نه استدلال خام بلند.
- **مسائل مبهم یا متناقض:** در پرامپت آمده اگر چند جواب معتبر وجود داشت کوچک‌ترین در ترتیب طبیعی انتخاب شود؛ در معماهای راستگو/دروغگو هر حالت جدا بررسی شود؛ در تناقض، سازگارترین تفسیر انتخاب شود و پاسخ هرگز خالی نماند. نتیجه‌ی رأی‌گیری هم در تساوی همین قاعده را اعمال می‌کند. توجه: در مسائل ۲، ۳ و ۱۰ Public بیش از یک جواب معتبر هست (۲: جایگاه اول B یا C؛ ۳: جعبه ۲ یا ۳؛ ۱۰: ۴۱۳ یا ۴۳۱). کلید استاد را نمی‌دانم، پس این قاعده یک حدس معقول است.
- **Thinking در Qwen3:** خروجی بین `<think>...</think>` قبل از استخراج جواب حذف می‌شود. پارامتر `think` اگر کتابخانه یا مدل پشتیبانی نکند خودکار کنار گذاشته می‌شود و از سوئیچ `/no_think` استفاده می‌شود.
- **مدیریت خطا:** خطای موقت سرور (مثل HTTP 503 یا قطع اتصال) ← تا ۳ بار تلاش مجدد با فاصله‌ی ۳، ۸ و ۱۵ ثانیه (این تلاش‌ها به‌عنوان فراخوانی جدید شمرده نمی‌شوند). Timeout ← بدون تلاش مجدد؛ ولی پاسخ مدل به‌صورت جریانی (streaming) خوانده می‌شود: اگر وسط تولید قطع شود متن نیمه‌کاره نگه داشته می‌شود، هر فراخوانی سقف زمان کل دارد، و به‌محض نوشته شدن یک خط کامل «FINAL ANSWER: ...» تولید متوقف می‌شود (صرفه‌جویی زمان). اگر مدل در حلقه‌ی تکرار بیفتد (یک متن بارها تکرار شود) تولید قطع می‌شود، و از متن ناتمام فقط یک خط کامل «FINAL ANSWER» پذیرفته می‌شود (هیچ عددی از خط نیمه‌نوشته برداشته نمی‌شود). جواب نامعتبر ← نمونه‌ی بعدی. اگر هیچ جواب معتبری نیامد، استخراج آزادتر از انتهای متن و در نهایت یک Fallback که فقط قالب معتبر دارد (حدس است، نه حل). `output.json` پیش از شروع حل با Fallback نوشته می‌شود و بعد از هر مسئله به‌روز می‌شود، پس حتی با قطع شدن برنامه معتبر می‌ماند.

### ساختار فایل‌ها
طبق قالب تمرین فقط سه فایل تحویل داده می‌شود و کل Agent داخل `main.py` است (هیچ پوشه‌ی دیگری لازم نیست):
```
main.py              نقطه‌ی ورود + کل Agent در پنج بخش پشت‌سرهم:
                     ANSWERS  نرمال‌سازی، تشخیص قالب، استخراج و اعتبارسنجی جواب (فقط پایتون)
                     MODEL    انتخاب مدل، تنظیمات، پوشش Ollama (streaming، تلاش مجدد، سقف زمان)
                     PROMPTS  همه‌ی پرامپت‌ها (انگلیسی؛ مثال‌های Few-shot ساختگی)
                     SOLVER   Baseline و Agent (Self-Consistency تطبیقی)
                     CLI      خواندن input.json و نوشتن output.json
requirements.txt
README.md
```
در زمان توسعه کد در چند فایل جدا بود (`agent/*.py`) و با ابزار `dev_tools/` (مولد مسائل با کلید brute-force، `eval.py`، تست‌های بدون مدل) آزمایش شد؛ سپس به یک `main.py` ادغام شد. خروجی ادغام‌شده روی ۸۶ مسئله و پنج حالت مدل جعلی دقیقاً با نسخه‌ی چندفایلی یکسان بود. این ابزارها جزو فایل‌های تحویلی نیستند.

## ۴. ارزیابی (Baseline در برابر Agent)

در زمان توسعه، مجموعه‌ها: `public` (۱۰ مسئله)، `dev` (۴۴ مسئله‌ی جدید و متنوع از ۱۲ نوع به‌علاوه‌ی نمونه‌های با اطلاعات بی‌ربط، مبهم و متناقض) و `holdout` (۳۲ مسئله با seed جدا، فقط برای تست نهایی).

دستورهای زیر در پروژه‌ی توسعه (خارج از فایل‌های تحویلی) اجرا شده‌اند:

```bash
python dev_tools/gen_problems.py                                  # (دوباره) ساخت مسائل
python dev_tools/eval.py --data dev --modes baseline,agent --repeats 3
python dev_tools/eval.py --data public --repeats 3
python dev_tools/eval.py --data holdout --modes baseline,agent --repeats 3   # فقط تست نهایی
python dev_tools/eval.py --data dev --think on                    # مقایسه‌ی thinking
python dev_tools/eval.py --data dev --modes agent --rewrite       # آیا بازنویسی کمک می‌کند؟
python dev_tools/test_plumbing.py                                 # تست سریع بدون مدل
```

در مسائل مبهم هر جواب معتبر درست حساب می‌شود و در مسائل متناقض فقط اعتبار قالب سنجیده می‌شود.

### نتایج

> همه‌ی عددها واقعی‌اند و روی لپ‌تاپ نویسنده (RTX 4050 با ۶GB VRAM، qwen3:8b، thinking خاموش) اندازه‌گیری شده‌اند. تعداد نمونه‌ها کم است (یک بار اجرا) و عددها نویزی‌اند. اجرای dev و Public با نسخه‌ی قبل از افزودن streaming انجام شد؛ اجرای holdout با نسخه‌ی نهایی (همین `main.py`) انجام شد و مسائل holdout هیچ‌وقت برای تنظیم کد استفاده نشده‌اند. سطرهای «—» هنوز اجرا نشده‌اند و حدس زده نشده‌اند.

## ۵. محدودیت‌ها

- تشخیص «چند جواب معتبر» با خود مدل است (طبق قوانین حل‌کننده‌ی زورکی در Agent مجاز نیست)، پس ممکن است گاهی خطا کند.
- قالب‌های جواب غیرمعمول با یک فراخوانی کوتاه از مدل تشخیص داده می‌شوند. اگر مدل آن را نفهمد، قالب «متن ساده» در نظر گرفته می‌شود و اعتبارسنجی ضعیف‌تر است.
- سقف زمان و فراخوانی پیش‌فرض بر اساس حدس است، چون حدود رسمی ارزیابی اعلام نشده است.
- مسائل مسیر روی شبکه (مثل مسئله‌ی ۹ Public) نقطه‌ضعف اصلی با qwen3:8b است: روی یک مجموعه‌ی ۶ مسئله‌ایِ خودساخته فقط ۰ تا ۲ مسئله درست شد؛ مدل گاهی از خانه‌ی مسدود عبور می‌کند یا در تکرار گیر می‌کند. مدل بزرگ‌تر احتمالاً بهتر است ولی روی آن اندازه‌گیری نشده است.
- سقف زمان (۳۰۰ ثانیه برای هر مسئله) و سقف فراخوانی (۶) حدسی‌اند و با محدودیت‌های اعلام‌شده‌ی مدرس باید تنظیم شوند (`--time-limit`، `--max-calls`).
- همه‌ی عددهای بالا با qwen3:8b به‌دست آمده‌اند؛ اجرای واقعی با qwen3.8:27b انجام نشده است.
